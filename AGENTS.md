# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

## Durable product decisions

- The main sidebar entry previously labeled “企业碳知识” is labeled “关注的企业”; keep its existing company-list navigation behavior.
- Following a company from the chat result adds it to the shared “关注的企业” list. The menu opens to the enterprise list only. A top-right “企业对比” action starts a separate 2–4 company selection step; confirming opens a dedicated comparison-detail page with an optional industry-median column, AI analysis, and report export. Do not place comparison or alert configuration directly on the initial enterprise-list page.
- Followed-company cards and compact-list rows show exactly the same enterprise fields: enterprise name, enterprise tags, unified social credit code, industry, stock type, and stock code. Omit region, update time, Scope 1+2, and carbon-target fields. The AI comparison analysis expands between the detail header and comparison table. Opening 华能 from this list reuses the same `/enterprise` archive as the management backend.
- The followed-enterprise header provides “添加企业” and “企业对比” actions. Adding uses a search-first flow: the modal is empty until the user searches by company name, security code, or industry, then adds individual results. It supports 10+ followed enterprises, currently capped at 12. A card opens the enterprise archive when clicked; its three-dot action reveals “取消关注” on hover. The comparison page keeps AI analysis but does not offer report export.
- Threshold alerts are managed from a dedicated “阈值提醒” action on the followed-enterprise list. A rule binds one followed enterprise to a carbon metric, trigger condition, threshold, and checking frequency; rules can be enabled, disabled, or deleted. Enterprise cards show the count of enabled rules.
- Keep 添加企业、阈值提醒、企业对比 on one horizontal row. The threshold-alert modal opens on a message inbox with unread status, triggered company, metric result, and trigger time, and provides a second tab for rule management.
- Creating a threshold alert supports selecting multiple followed enterprises and adding multiple monitoring metrics in one operation. Each selected metric has its own trigger condition and threshold; submission creates the enterprise × metric rule set.
- The followed-enterprise list shows an alert-message module directly above the search toolbar only when messages exist, with at most five visible messages and a “查看更多” action opening the full message page. Threshold-rule configuration opens as a dedicated page from the header action; do not use a modal for rule settings.
- Every followed-enterprise card navigates to the shared enterprise archive route with its company ID. Deployed navigation must use the app base path and hash routing (`/agent_data/#/enterprise?...`) so GitHub Pages never resolves it against the account root. Asset URLs must also respect `import.meta.env.BASE_URL`.
- Hash-only route changes must reload the current document after updating the URL because the prototype does not use a client router; otherwise the address changes while the mounted list view remains visible.
- Enterprise archives opened from the followed list show a “返回关注企业” action that routes back to the followed-enterprise list. In the current prototype, archive operations (export, smart interpretation, and data export) are hidden, and the data-dimension sidebar exposes only carbon emissions; ESG and product carbon footprint remain hidden.
- Enterprise archives opened from the followed-enterprise list retain the main Carbon Agent left navigation with “关注的企业” active; render the archive in the right workspace. Direct management-backend archive routes keep their existing standalone/backend layout.
- In followed-enterprise archives, place the data-dimension navigation as a horizontal tab bar directly below the enterprise registry-information card and above the dimension content. Show 碳排放 as the active tab and remove the duplicate left-side dimension card in this context.
- The followed-enterprise list defaults to cards and supports switching to a compact list. Populate enough sample records to evaluate both layouts. Comparison details support reporting-year switching and use the source carbon schema: Scope 1, Scope 2 market/location/unknown, Scope 3, combined totals, and revenue-intensity variants. Every quantitative indicator has a trend-chart action opening a modal with multi-year bars and year-over-year line.
- Enterprise query results stream rows progressively and contain a two-column enterprise-basic-information table, a separate business-scope block, and a carbon-emissions table preserving Scope 2 market/location methods, Scope 3, combined totals, intensity, and reporting year. Do not show the comparability check, industry benchmark table, right-side key insights, or followed-company comparison action in this result flow.
- The bottom of an enterprise query result contains a data-source report table with title, publication date, type, and source columns.
- The first Agent application-layer scenario uses the “对话即工作台” flow: natural-language enterprise carbon questions trigger an explicit enterprise-carbon-data MCP state, return an evidence-backed company-versus-industry benchmark table, and expose company follow, followed-company comparison, and full industry-position actions from the result.
- Enterprise-carbon questions must follow an interactive entity-resolution sequence: accept the user's question, call the enterprise-carbon-data MCP, return matching enterprise subjects for confirmation, and only after confirmation combine the original question with that enterprise's structured carbon records to generate the answer.
- Enterprise matching results display every candidate in a fixed compact card with only the full enterprise name, enterprise tags, stock type, and stock code. Do not expand registry details after selection, show match-confidence percentages, or add a separate selected-accounting-subject/boundary block in the confirmation step.
- Enterprise benchmark answers must expose a comparability preflight covering year, organizational boundary, Scope 2 method, and intensity denominator. The full carbon portrait uses the “enterprise fact / industry position / Agent explanation” structure. Following a company includes selectable monitoring purposes that shape later comparisons and alerts.

- Enterprise carbon knowledge answers use a report-style natural-language structure: 15 numbered dimensions in priority order, continuous prose, bullets or data tables where appropriate, and inline file citations.
- Enterprise archive dimension details use a two-column form layout rather than list/table rows. Each field shows its label, latest value/status, and reporting period only; do not show evidence source or evidence status inside dimension forms.
- Enterprise disclosure source files remain a separate module and must support filtering by year and file type.
- Enterprise confirmation cards show five explicit basic-information fields: enterprise name, enterprise code, industry, listing venue, and security code.
- The management backend lives at `/admin`. In the left operations navigation, `企业碳数据` is a first-level item immediately below and at the same level as `企业碳核算`. It expands to three second-level pages: 数据概览、企业列表、字段管理. The 华能国际 row in 企业列表 opens the existing `/enterprise` enterprise-detail prototype.
- The management enterprise list uses source registry fields: enterprise name, unified social credit code, legal representative, registration status/company type, establishment date, and industry. Do not show derived archive completeness, source-file counts, update time, archive-status, or data-quality columns/filters there. The enterprise archive overview shows the five basic identity fields (name, enterprise code, industry, listing venue, security code) followed by completeness for all 15 carbon-management dimensions.
- The management data overview keeps three summary metrics: 企业总数、披露源文件、高质量档案. Do not show 已建碳档案, MVP 档案覆盖, or 数据源运行状态. 企业库增长趋势 and 行业分布 use the full content width.
- Enterprise主体 uses a normalized enterprise-entity model: stable entity identifiers and listing records belong to the entity; parent/subsidiary ownership, effective dates, consolidation status, disclosure identity, and carbon-accounting boundaries are separate relationship records. Its detail view groups fields into entity registration, listings, and group/accounting relationships and includes a group hierarchy tree.
- 排放核算 records must identify the accounting subject and level (group/legal entity/facility) before presenting emissions, with entity/facility inclusion lists, consolidation method, Scope 3 boundary, offsets/removals, data quality, and assurance scope. 目标与承诺 records must bind each target to its responsible entity, applicable group level, covered entities/scopes, baseline and target values, progress method, offset reliance, governance, and change history.
- 排放核算 supports switching by reporting year. 目标与承诺 supports switching among all, near-term, medium-term, and long-term target cycles. 披露与证据 directly contains the year/type-filterable source-file library; do not keep a separate source-file navigation item or duplicate source library at the bottom.
- 企业主体 separates entity registration, business/operating scale, securities listings, and group/accounting relationships. Preserve ESG-report-native fields such as principal business, products, operating regions, facilities, employees and revenue, while external registry identifiers remain enrichment data rather than being mixed into report extraction results.
- 排放核算 uses an emission-fact grain: company × source report × data period × boundary/entity/facility × Scope/category × metric. Preserve raw and standardized values/units together, distinguish Scope 2 location/market methods and unspecified totals, and bind intensity to numerator Scope, denominator type, currency and scale. Activity data, factor versions, restatements and assurance scope remain traceable fields.
- The public enterprise intelligence profile lives at `/enterprise`. Beneath the enterprise identity header, keep exactly three first-level data dimensions: 碳排放、ESG、产品碳足迹. Carbon covers accounting, trends, targets, energy and assurance; ESG covers reports, ratings, awards, and environmental/social/governance performance; product carbon footprint lists every product with disclosed accounting in visual cards showing the product image, name/model, result, functional unit, period, and boundary. Do not reintroduce unrelated enterprise-data dimensions on this profile.
- The `/enterprise` carbon dimension follows the Qinglv-style five-year field matrix (2025–2021). Keep three field groups: 温室气体管理（政策、措施、目标）, 碳排放量（Scope 1/2/3 and combined totals）, and 碳排放强度（unit-revenue Scope 1/2/3 and combined intensities). Preserve missing years as `—`, disclosure links as `查看`, and year-specific raw values instead of collapsing them into a latest-value-only table.
- Enterprise identity and registry information is a single non-dimension block between the company hero and the two data dimensions. Display every industrial-and-commercial field directly in its top summary; do not repeat a separate 工商信息 detail grid or any related-information shortcut row.
- The public enterprise hero shows only the company mark, company name and classification tags. Do not repeat listing/verification badges or the securities/industry/region/credit-code metadata row above the structured enterprise-information card.
- The enterprise-detail route starts with a compact breadcrumb (`企业碳数据 / 企业列表 / 企业 / 当前维度`) instead of a public-site global navigation bar. Carbon details omit the standalone target/action card, the 温室气体管理 policy group, the KPI summary cards and the five-year trend chart, so the dimension opens directly on the structured indicator table. Scope 3 remains collapsed by default and expands inline to the 15 GHG Protocol categories.
- Trend affordances are reserved for quantitative metrics with a concrete unit and at least one numeric annual value. Clicking either a quantitative metric name or its trend icon opens a modal with annual bars, year-over-year change, and a detail table. Scope 3 uses an icon-only expand/collapse control with an accessible label.
- The `/enterprise` ESG dimension uses three second-level performance groups—环境绩效、社会绩效、治理绩效—with Qinglv-style pill subcategories. Environment contains only 能源、水资源、污染物、废弃物; social contains 人力资源、薪酬与福利、培训与发展、健康与安全、产品责任、供应商、公益与扶贫; governance contains 股权与股东、董事会、监事会、高管层、信息披露、对外担保、违规经营、反贪污、公司党建、股东回报、投资者关系. Each selected subcategory renders a 2025–2021 structured field matrix and supports disclosure/detail interactions.
- The ESG dimension begins with an ESG report history table (发布日期、标题、类型、来源), paginated ten records per page. Do not show the aggregate ESG score/rating overview or the compact ESG资料库. Environment, social and governance are three consecutive independent modules on the same page—not a mutually exclusive top-level switch—and each keeps its own Qinglv-style subcategory selector and five-year matrix.
- The public enterprise hero does not show archive completeness or a monitor-company action, and the data-dimension sidebar does not show the trusted-data-source summary.
- In carbon and ESG annual indicator matrices, keep the 指标 and 单位 columns fixed while the year columns scroll horizontally.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
